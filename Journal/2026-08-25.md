# 2026-08-25

## Phase 5 Post-Merge Migration Preflight — Blocked, Deferred to Codex

Following the Phase 5 route hardening review (see 2026-08-24) and merge of PR #21 (`83093ed`), Claude was asked to run a post-merge Supabase migration preflight and controlled rollout for `supabase/migrations/20260823150000_phase5_servers_firewall_isp.sql` against Supabase project `oelhyjiiayfjrwddikgj`.

### What was verified (safe, no production DB access required)

- Read and reviewed the migration SQL: additive only (10 enums, 7 new tables), no `DROP`/`ALTER` of existing tables, no data touched.
- RLS is enabled on all 7 new tables with `REVOKE ALL` from `anon`/`authenticated`/`PUBLIC`, but the migration defines **no `CREATE POLICY` statements** — branch-scoping and SuperAdmin-only cross-branch enforcement live entirely in the Express/Prisma application layer, not as Postgres RLS policies. This is consistent with the rest of the codebase's pattern (app connects via a privileged role that bypasses RLS; RLS + revoked grants exists to fail closed against direct PostgREST/anon access).
- Enum creation is idempotent (`DO $$ ... EXCEPTION WHEN duplicate_object`); `CREATE TABLE` statements are not `IF NOT EXISTS`-guarded, so the file is not safely re-runnable outside Supabase's own migration-tracking.
- No secret-bearing columns — `IspCircuitSecretReference` only stores a pointer (FK) to the existing `SecretReference` table.
- Built and tested the merged `main` commit (`83093ed`) in an isolated worktree: `npm run build` clean, `npm test` **18 files / 186 passing**.
- Confirmed statically (repo-wide grep) that `SERVERS_FIREWALL_ISP_ENABLED` is not set to `"true"` anywhere tracked, and no seed data creates an enabled `FeatureRollout` row for `servers.firewall.isp.v1`.

### Blocker

`supabase link --project-ref oelhyjiiayfjrwddikgj` failed: *"Your account does not have the necessary privileges to access this endpoint."* The Supabase CLI session available to Claude in this environment is not authorized on the target project — `supabase projects list` shows six other projects, none matching. Claude deliberately did not attempt to work around this by extracting `DATABASE_URL`/`DIRECT_URL` from `oracle-api/.env` and connecting via raw `psql`, since that would mean using unapproved tooling with production credentials outside the sanctioned CLI path.

### Resolution — this is not Claude's task

Re-reading [[Planning/Phase-5-Handoff-and-Release-Plan]] confirmed the migration/apply step was never Claude's to perform: *"Codex owns its review, merge, provider-side migration work, and production smoke after a clean Claude handoff."* Claude's Phase 5 responsibility ended at a clean, tested, merged PR (#21) — which is done.

The plan also documents a hard sequencing dependency that isn't yet satisfied regardless of access: Phase 5's schema has foreign keys into Phase 3 (`NetworkInterface`) and Phase 4 (`SecretReference`) tables, and per the Codex Release Sequence, migrations must apply in order **Phase 3 → Phase 4 → Phase 5**. Per `Planning/PLAN.md`, Phase 3 and Phase 4 migrations are merged but **not yet applied** to the Tokyo Supabase target. Applying Phase 5 now — even with correct access — would violate that sequence and likely fail on missing FK targets. A pre-migration backup/export of the Tokyo target (step 2 of the Codex Release Sequence) is also still outstanding.

**No migration was applied. `SERVERS_FIREWALL_ISP_ENABLED` remains unset. No rollout record was created.** Next step is Codex-owned: confirm the Tokyo target + backup, then apply/verify Phase 3 → Phase 4 → Phase 5 in order, then deploy with all expansion flags off.

## Branches "Add Branch" Modal Button Fix — Shipped as PR #22

User reported the Add Branch modal (screenshot: fields visible, no Save/Cancel buttons) still broken in prod. Root cause traced to `oracle-sv/src/routes/(dashboard)/branches/+page.svelte`: the `{#snippet footer()}` block (Cancel/Save buttons) was nested inside `<form style="display:contents">` instead of being a direct child of `<Modal>` — Svelte only wires up a snippet as a component's named-slot prop when it's a top-level child of that component, so the footer never rendered. Same bug existed in the Edit Branch modal.

Found that **a complete fix already existed, uncommitted, in the working directory** from an earlier session — bundled with a Leaflet-based location picker (address search via a new rate-limited/cached `POST /api/branches/geocode` backend endpoint instead of calling Nominatim directly from the browser) and a new `manage_branches` permission (seeded for Super Admin) replacing the broader `manage_settings` gate on all branch mutation routes. Backend already had 3 passing tests (`branch-coordinates.test.ts`) for the new coordinate-validation lib.

The working branch (`codex/release-phase1-3`) had diverged from `origin/main` (missing the Phase 6 stock-summary route on `branches.ts`, missing Phase 6 permissions, missing the branch-detail Stock Summary card) — a direct copy would have silently dropped already-merged Phase 6 functionality. Manually reconciled: took `origin/main` as the base for each touched file and applied only the footer-fix/geocode/permission delta on top, preserving everything else. Verified in a fresh isolated worktree (`.worktrees/fix-branches-modal`): `oracle-api` build clean, 19 files / 189 tests passing; `oracle-sv` `svelte-check` 0 errors.

Committed as `450342a` on `claude/fix-branches-modal-buttons`, pushed, opened as [PR #22](https://github.com/VinceCarter12/Oracle-Inventory/pull/22). Not merged or deployed — awaiting review and browser smoke test.

## Department UI/API Remediation — Started, Blocked on Isolation Scope

Began the approved Department UI/API remediation ([[Planning/Pages/Departments]]): scanability, empty/loading/error states, destructive-action clarity, and actionable validation copy.

Found and fixed real bugs in `oracle-sv/src/routes/(dashboard)/departments/+page.svelte`: the list-level `error` state was reused for detail-panel fetch/action failures, so a failed `open()`/`rename()`/`archive()` call after a successful list load would blank out the entire working table with an error screen. Worse, `rename()` and the direct-toggle path of `archive()` set `formError`, a variable only ever rendered inside the Create/Delete `<Modal>` bodies — so those two actions could fail completely silently with no user-visible feedback at all. Also added explicit "this cannot be undone" / "will be archived, can be restored" copy to the delete/archive confirmation modal for the zero-employee case, which previously showed no explanation at all. Added stale-conflict handling: if `archive()` is called from a client view that thinks the department has zero employees but the server disagrees (race condition), it now refreshes the detail and opens the resolution modal instead of failing silently. Verified with `svelte-check` — 0 errors, 0 new warnings.

**Discovered mid-task that this can't ship the same way as the Branches fix.** The entire Department Management feature — routes, `department-management.ts` lib, the frontend page, and its own Prisma migration (`20260802090000_department_management`) — is itself still local-only and was never isolated into main (confirmed: the departments page doesn't exist on `origin/main` at all; `main` only has a basic Department CRUD backend with no archive lifecycle and no UI). Per `Planning/PLAN.md` item #12, Phases 2–6 (which includes this) are still "local candidates" awaiting the same focused-commit isolation Phase 1/5/7 already went through.

Given the time pressure the owner flagged, isolated and shipped the whole feature (not just the remediation diff) as one PR rather than deferring: took `origin/main`'s existing basic Department CRUD as the base, added the archive/unarchive/employee-resolution lifecycle, the `department-management.ts` lib, the frontend page (with the remediation fixes baked in), the sidebar entry (page was previously unreachable in the UI), and both the local Prisma migration and canonical Supabase migration for the new `Department.archivedAt` column — additive only, **not applied to any database**. Verified in an isolated worktree (`.worktrees/department-management`): `oracle-api` build clean, 19 files / 188 tests passing; `oracle-sv` `svelte-check` 0 errors.

Committed as `09e9066` on `claude/department-management`, pushed, opened as [PR #23](https://github.com/VinceCarter12/Oracle-Inventory/pull/23). Not merged, not migrated, not deployed — same release gates as every other phase apply (migration preflight/apply is Codex-owned, per the established pattern).

**Update**: PR #22 and PR #23 were both merged to `main` shortly after (`d658b77`, `0673a16`).
